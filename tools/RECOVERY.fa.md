# بازیابی سایت نگهداری‌شده و آزمایش واقعی از خود میزبان

این ابزار فقط در **Bash console مالک حساب PythonAnywhere** اجرا می‌شود. عامل
گفتگو به آن کنسول یا نشست مدیر دسترسی ندارد. 503 نگهداری حتی مسیر استقرار
امضاشده را می‌بندد؛ از HTTP نمی‌توان نسخهٔ رفع اشکال را روی چنین نصبی نصب کرد.
احراز هویت و سیاست maintenance عمداً دور زده نمی‌شوند.

## مسیر پیشنهادی

فرمان زیر برای نصب با مسیر پیش‌فرض است. اگر Web → Source directory متفاوت است،
متغیر `S4_INSTALL_DIR` را به **همان نصب موجود** بدهید؛ محیط مجازی متفاوت با
`S4_VENV` قابل تعیین است. ابزار در صورت نبود دیتابیس/کلید قبلی متوقف می‌شود.

```bash
cd "${S4_INSTALL_DIR:-$HOME/scraper4-python/pythonanywhere}" && \
helper="$(mktemp)" && \
curl -fsSL 'https://raw.githubusercontent.com/fazilatma/new/arena/f3d5d2a0-new/tools/recover_live_install.py' -o "$helper" && \
"${S4_VENV:-$HOME/.virtualenvs/scraper4}/bin/python" "$helper" --app-dir "$PWD" --recover-code --probe-all
```

- بدون `--recover-code` فقط وضعیت snapshot بررسی می‌شود؛ حتی marker هم حذف نمی‌شود.
- بازیابی تحت قفل worker و فقط برای marker دست‌کم دو دقیقه‌ای است. قفل فعال را
  آزاد یا فرایند را kill نمی‌کند. snapshot باید در releases همین نصب باشد؛
  تفاوت dependency، DB code یا deployment authority را رد می‌کند.
- از `updates.rollback` نصب موجود استفاده می‌کند: ابتدا کد snapshot در دیتابیس
  موقت validate می‌شود؛ **فقط کد** برمی‌گردد، سپس Reload با تنظیمات رمز‌شدهٔ خود
  میزبان درخواست می‌شود. DB زنده از backup بازگردانی نمی‌شود، کلید ساخته یا
  تعویض نمی‌شود. autoupdate طبق مسیر rollback خاموش و درخواست مبهم قبلی failed
  می‌شود تا خودکار دوباره اجرا نشود.
- از فرمان `maintain` استفاده نمی‌کند، زیرا آن فرمان بعد از نگهداری `tick` اجرا
  می‌کند. این ابزار هرگز tick، worker، صف ارسال/استخراج یا کران را اجرا نمی‌کند.
- پس از بازیابی، تشخیص در **مفسر تازه** اجرا می‌شود تا ماژول‌های قبل از rollback
  با کد نصب‌شده مخلوط نشوند. `--probe-all` به‌صورت ترتیبی یک صفحه از مبدأهای مستقیم
  پروفایل‌های واقعی نصب را با موتور ذخیره‌شده آزمایش می‌کند. GitHub صریحاً skipped
  است. گزارش آزمایش checkpoint ذخیره می‌کند؛ محصول/صف ایجاد یا تغییر نمی‌دهد و
  هیچ درخواستی به فروشگاه مقصد برای ارسال ندارد. workerهای زمان‌بندی‌شدهٔ موجود
  ممکن است مستقل کار کنند؛ این گزارش snapshot سراسری اتمی نیست.
- با Ctrl+C بررسی متوقف و گزارش ناقص ذخیره می‌شود. فایل خروجی جدید، محلی و mode600
  است؛ مسیر فایل موجود بازنویسی نمی‌شود. مسیر پیش‌فرض:
  `~/scraper4-live-YYYYMMDDTHHMMSS.json`؛ با `--report /path/to/NEW.json` قابل تعیین است.
- قالب گزارش به‌وضوح `installed_local_wsgi_on_host_not_external_http` است: اپ واقعی
  و دیتابیس واقعی میزبان، بدون mock/fixture، ولی **نه درخواست HTTP خارجی به پنل**.
  اختیار محلیِ مالک برای فراخوانی WSGI در همان فرایند استفاده می‌شود؛ کوکی/نشست یا
  توکن قابل استفاده از راه دور ساخته یا اشتراک‌گذاری نمی‌شود. اثرگذاری واقعیِ
  کلید، موجودی، قیمت یا ارسال مقصد بررسی نمی‌شود.
- اگر snapshot معتبر نیست یا validation/Reload شکست خورد، marker خودسرانه حذف
  نمی‌شود. متن خطا/لاگ/کلید خام چاپ نمی‌شود. در آن حالت نصبگر CLI و لاگ خصوصی میزبان
  باید بررسی شوند؛ تکرار کورکورانه یا `rm .maintenance.json` توصیه نمی‌شود.

فایل را قبل از پیوست‌کردن در گفتگو بازبینی کنید: نام پروفایل‌ها، وضعیت صف و نتیجهٔ
آزمایش داخل آن هستند. رمز، کوکی، CSRF، URL خصوصی و امضای ادامهٔ probe در فایل نیستند.
پس از اجرای موفق، سلامت **HTTP خارجی** باید جداگانه با نسخه و commit دقیق بررسی
شود؛ موفقیت CLI/Reload به‌تنهایی استقرار زندهٔ نسخهٔ جدید را ثابت نمی‌کند.

## خطای کلی Maintenance failed در نصب قدیمی، بدون کپی کنسول

`tools/diagnose_update.py` یک preflight مالک‌محور و مستقل از نسخهٔ نصب‌شده است. آن را با Python محیط **همان نصب موجود** اجرا کنید؛ نیازی به نصب نسخهٔ جدید برای تشخیص نیست. `.env` و DB موجود لازم‌اند؛ ابزار برای HTTP عمومی register نمی‌شود. مسیر پیش‌فرض `/home/<owner>/scraper4-python/pythonanywhere` و گزینهٔ مالک‌محور `--app-dir` دارد.

کارهایش: قفل مشترک worker، رد maintenance marker یا درخواست pending/running، resolve شاخهٔ نصب از updater موجود، یک دانلود/بازکردن بستهٔ ثابت (حداکثر8MiB و45ثانیه)، مقایسهٔ requirements بدون pip، compile و validation مطابق updater با DB موقت، کپی آزمایشی کد/SQLite در scratch زیر releases، و بررسی مجوز نوشتن فایل‌های مدیریت‌شده. scratchها پاک می‌شوند. نصب/جایگزینی کد، Reload، rollback، پاک‌کردن marker، ادامهٔ صف، تغییر token یا probe مبدأ انجام نمی‌دهد. تغییر requirements گزارش می‌شود و import/install آن اجرا نمی‌شود. این پیش‌بررسی **تست نصب یا Reload نیست**؛ موفقیت آن به معنی رفع خرابی یا فعال‌شدن نسخه نیست.

نام stage شکست، دستهٔ امن خطا (permission/disk_quota/archive/validation/...)، errno و شماره‌خط فایل‌های ازپیش‌مجاز ثبت می‌شود؛ هیچ raw exception/traceback/source/locals/URL/credential خروجی نمی‌شود. تنها نوشتن پایدار DB، فیلد `state.diagnostic` در checkpoint `updates:state` است که با transaction با فیلدهای قبلی merge می‌شود. این گزارش از `/api/updates/status` نسخهٔ قدیمی نیز خوانده می‌شود؛ مالک لازم نیست خروجی کنسول را کپی کند. تغییر محصول/پروفایل/صف/تنظیم زمان‌بندی یا وضع عملیات ندارد. خطای نوشتن گزارش نیز فقط دستهٔ امن در کنسول می‌دهد؛ در آن حالت عکس خروجی امن کافی است.

در بررسی زندهٔ این مرحله، نسخه1.25فعال و selftest سالم بود؛ عملیات update آخر failed، latest برابر `fbc593e85b9d5f4ff3774261775ba63255ce7250` ثبت شده بود. پس lookup نسخه انجام شده، اما مرحلهٔ دقیق شکست از پیام generic قابل تعیین نیست. ابزار باید **روی میزبان مالک** اجرا شود؛ تست‌های محلی/fixture اثبات اجرای preflight میزبان نیستند. به‌جای تکرار کورکورانهٔ استقرار/آپدیت، پس از اجرای ابزار گزارش خواندنی را بررسی کنید.
