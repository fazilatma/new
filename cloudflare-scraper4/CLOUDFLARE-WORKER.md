# Scraper 4 روی Cloudflare Workers

این پوشه نسخهٔ Cloudflare-native از `scraper4.php` نسخهٔ 9.80 است. برنامه از Worker ماژولی، D1، Queues، Cron Triggers و Web Crypto استفاده می‌کند و به Node.js، PostgreSQL، Bash یا فایل‌سیستم دائمی وابسته نیست. پشتیبانی runtime از R2 اختیاری است، اما استقرار پیش‌فرض برای کار بدون کارت بانکی هیچ R2 binding ندارد.

## معماری

- `worker-src/main.ts`: entrypoint و handlerهای `fetch`، `queue` و `scheduled`
- `worker-src/app.ts`: API و داشبورد Hono، import/export، diagnostics و routeهای سازگاری (طبق تصمیم مالک بدون صفحهٔ ورود و `ADMIN_TOKEN`)
- `worker-src/db.ts` و `migrations/`: persistence، bootstrap مقاوم و migrationهای D1
- `worker-src/processor.ts`: پردازش chunked با checkpoint، توقف، retry، watchdog و ادامه در Queue
- `worker-src/scraper.ts`: استخراج فهرست/جزئیات با `HTMLRewriter`، JSON-LD و pagination کامل، شامل `next_selector`
- `worker-src/sync.ts`: WooCommerce و Basalam چندغرفه‌ای با destination map
- `worker-src/vault.ts`: رمزنگاری اتصال‌ها با PBKDF2-SHA256 و AES-GCM
- `worker-src/network.ts`: محدودسازی URL، redirect، timeout و اندازهٔ پاسخ
- `worker-src/parity.ts`: inventory دقیق 57 عملیات منوی PHP و self-test
- `scraper4.worker.js`: bundle تولیدشده و آمادهٔ Direct Upload برای به‌روزرسانی‌های بعدی

D1 منبع canonical داده است. Queue فقط شناسهٔ job را حمل می‌کند و checkpoint هر job در `app_state` می‌ماند؛ بنابراین redelivery یا restart باعث از دست‌رفتن progress نمی‌شود. هر delivery حداکثر `JOB_CHUNK_SIZE` محصول را پردازش می‌کند.

### مشخصات اجرایی Cloudflare، نه یک سرور ثابت

Worker ماشین مجازی اختصاصی با CPU یا vCPU قابل‌انتخاب نیست؛ در V8 isolateهای Cloudflare روی شبکهٔ جهانی اجرا و خودکار scale می‌شود. طبق [Limits رسمی](https://developers.cloudflare.com/workers/platform/limits/) در پلن Free حدود مهم عبارت‌اند از: **128 MB حافظه برای هر isolate، 10 ms زمان CPU برای هر HTTP request، 100,000 درخواست در روز، 50 subrequest و 6 اتصال خروجی همزمان برای هر invocation، bundle فشردهٔ 3 MB و startup حداکثر 1 ثانیه**. انتظار پاسخ شبکه CPU time محسوب نمی‌شود. درخواست HTTP hard wall-time عمومی ندارد، ولی به باز ماندن client وابسته است؛ Queue/Cron/Alarm حداکثر 15 دقیقه wall-time و `waitUntil()` حداکثر 30 ثانیه پس از response/disconnect فرصت دارد.

در پلن Paid حافظه همچنان 128 MB است؛ CPU درخواست HTTP به‌طور پیش‌فرض 30 ثانیه و قابل افزایش تا 5 دقیقه و subrequest پیش‌فرض 10,000 است. سقف body ورودی به plan اصلی حساب Cloudflare وابسته است (Free/Pro برابر 100 MB)، نه صرفاً Workers plan. جدول کامل، معنای connection و محدودیت bundle در [`CLOUDFLARE-PARITY.md`](./CLOUDFLARE-PARITY.md) ثبت شده است. dry-run نسخهٔ 1.1.0 پروژه فقط **842.75 KiB upload / 194.41 KiB gzip** است.

پروژه برای پلن Free تنظیم شده: `DETAIL_CONCURRENCY=2`، `JOB_CHUNK_SIZE=10`، checkpoint در D1 و Queue برای ادامهٔ کار. این adaptation به‌جای نگه‌داشتن یک process طولانی PHP، هر اجرا را کوچک و قابل retry می‌کند.

## استقرار کامل فقط با Cloudflare Dashboard

برای نصب نخست **هیچ D1 یا Queue را دستی نسازید**. `wrangler.toml` resourceها را با نام قطعی و بدون ID حساب تعریف می‌کند و `npm run worker:deploy` همهٔ آن‌ها را ایجاد، متصل و migrate می‌کند. این کار در محیط Workers Builds اجرا می‌شود؛ کاربر به terminal، Bash، R2 subscription یا کارت بانکی نیاز ندارد.

R2 عمداً در تنظیمات production تعریف نشده است، زیرا فعال‌سازی آن checkout و روش پرداخت می‌خواهد. endpoint عادی `/api/backup` همچنان backup کامل JSON را برای نگه‌داری روی دستگاه کاربر دانلود می‌کند. فقط حالت اختیاری `persist=true` که backup را مستقیم داخل R2 نگه می‌دارد در این استقرار غیرفعال است.

> نام Worker را دقیقاً `scraper4-cloudflare` بگذارید. نام Queueها ثابت است و consumer عمداً به همان نام‌ها اشاره می‌کند.

### 1. اتصال GitHub به Workers Builds

1. در Cloudflare Dashboard به **Workers & Pages** بروید.
2. **Create application / Import a repository** را انتخاب کنید و repository را از GitHub متصل کنید.
3. نام Worker را `scraper4-cloudflare` قرار دهید.
4. شاخهٔ production را `arena/01a0765b-new` انتخاب کنید.
5. Root directory را `cloudflare-scraper4` بگذارید.
6. در **Build variables and secrets** متغیر build زیر را اضافه کنید تا فایل Python قدیمی repository نصب نشود:

   ```text
   SKIP_DEPENDENCY_INSTALL=1
   ```

7. Build command را این مقدار بگذارید؛ `npm ci` وابستگی‌های Worker را نصب می‌کند:

   ```text
   npm ci && npm run worker:test
   ```

8. Deploy command را این مقدار بگذارید:

   ```text
   npm run worker:deploy
   ```

9. Preview deploy برای شاخه‌های دیگر را غیرفعال کنید تا resourceهای production توسط buildهای preview تغییر نکنند.
10. **Save and Deploy** را بزنید.

Git integration پس از هر push جدید به شاخهٔ production، repository را خودش checkout و build می‌کند. Worker در runtime دستور `git pull` اجرا نمی‌کند و نباید هم‌زمان یک GitHub Actions deploy جداگانه فعال شود.

### 2. resourceهایی که deploy خودکار می‌سازد

Wrangler قفل‌شده در `package-lock.json` هنگام نخستین deploy این موارد را provision می‌کند:

| نوع | binding | نام resource ساخته‌شده | اتصال خودکار |
|---|---|---|---|
| D1 | `DB` | `scraper4-cloudflare-db` | بله |
| Queue اصلی | `JOBS` | `scraper4-cloudflare-jobs` | producer + consumer |
| Dead-letter Queue | `JOBS_DLQ` | `scraper4-cloudflare-jobs-dlq` | DLQ برای `JOBS` |
| Cron Trigger | — | `* * * * *` | بله |
| Workers Logs | — | invocation logs | بله |

وجود producer دوم `JOBS_DLQ` عمدی است: Wrangler ابتدا DLQ را می‌سازد و سپس consumer اصلی را با `dead_letter_queue` نصب می‌کند. برنامه لازم نیست روی این binding پیام عادی بفرستد.

اسکریپت `scripts/deploy-cloudflare.mjs` سه مرحلهٔ غیرتعاملی دارد:

1. `wrangler deploy` با automatic provisioning؛
2. اجرای تمام migrationهای pending روی binding خودکار `DB`؛
3. smoke واقعی روی URL عمومی production برای `/health`، `/api/version` و `/api/debug`؛ نسخه، D1 و Queue نیز اعتبارسنجی می‌شوند و build در صورت شکست smoke موفق اعلام نمی‌شود.

همهٔ مراحل idempotent هستند. resourceها نام قطعی دارند اما ID حساب در Git ذخیره نمی‌شود؛ بنابراین حتی اگر deploy پس از ساخت یک resource قطع شود، retry همان resource را با نام پیدا و متصل می‌کند و نمونهٔ تکراری نمی‌سازد. deployهای بعدی نیز فقط migrationهای جدید را اعمال می‌کنند. علاوه بر آن، `ensureSchema()` در شروع هر isolate تمام دستورهای `CREATE ... IF NOT EXISTS` را یک‌بار اجرا می‌کند تا database تازه یا نیمه‌کاره نیز خودکار ترمیم شود.

در log نخستین build باید پیام‌های provisioning/اتصال برای `DB`، `JOBS` و `JOBS_DLQ` و سپس پیام موفقیت migration دیده شوند. هیچ درخواست R2 یا خطای `10042` نباید وجود داشته باشد. اگر build در میانه قطع شد، **Retry deployment** امن است و resource تکراری ایجاد نمی‌کند.

### 3. افزودن secretها از Dashboard

ساخت resource با ساخت secret متفاوت است؛ secret امن را نمی‌توان داخل Git تولید یا commit کرد. پس از موفقیت نخستین deploy:

1. Worker `scraper4-cloudflare` را باز کنید.
2. به **Settings → Variables and Secrets** بروید.
3. `VAULT_SECRET` را به‌صورت **Secret** و با یک مقدار تصادفی حداقل ۸ کاراکتری اضافه کنید.
4. تغییرات را Save/Deploy کنید و URL `workers.dev` را باز کنید.

ورود پنل و API فعلاً به `ADMIN_TOKEN` نیاز ندارد. `VAULT_SECRET` کلید رمزگذاری vault است و پس از ذخیرهٔ اتصال‌ها نباید تغییر یا حذف شود. برای restore یک backup روی استقرار دیگر نیز همان `VAULT_SECRET` لازم است.

متغیرهای credential مقصد مانند `WOO_URL`، `WOO_KEY`، `WOO_SECRET` و `BASALAM_TOKEN` فقط fallback هستند. روش پیشنهادی، ثبت اتصال‌ها از پنل رمزگذاری‌شدهٔ خود برنامه است. هیچ secret حساسی را در `wrangler.toml` قرار ندهید.

### 4. کنترل نصب از مرورگر

بعد از تعریف secret:

- `https://<worker>.workers.dev/health` باید `ok: true`، `databaseReady: true` و `authenticationRequired: false` بدهد.
- داشبورد باید بدون کادر ورود مستقیماً اطلاعات را بارگذاری کند.
- endpoint `/api/selftest` باید بدون توکن `ok: true` و `total: 57` نشان دهد.
- endpoint `/api/debug` باید بررسی‌های runtime، vault، D1 و Queue را بدون نمایش مقدار Secret برگرداند.
- `/api/parity` خلاصهٔ 178 dispatcher و inventory سطح منو را نشان می‌دهد؛ matrix کامل در `parity-manifest.json` است.
- در **Bindings** باید `DB`، `JOBS` و `JOBS_DLQ` دیده شوند؛ نبودن `BACKUPS` عمدی است.
- در **Triggers** باید Cron پنج‌دقیقه‌ای و Queue consumer دیده شوند.

نیازی به D1 Console، R2، ساخت Queue، paste کردن UUID یا اجرای migration دستی نیست.

## مهاجرت داده از PHP

دو مسیر وجود دارد:

1. در داشبورد Worker، **تنظیمات عمومی ← انتقال همه تنظیمات** را باز کنید و bundle خروجی PHP را import کنید.
2. فقط برای `profiles.json` قدیمی، درخواست `POST /api/import-php` بدون هدر ورود قابل استفاده است.

فرمت `scraper4-php-compatible` برای فایل‌های اتصال، تنظیمات، category learning، autoreply، profile/product و variation پشتیبانی می‌شود. `syncConfig`، `src_network`، پروفایل‌های `noExtract`، fallback category و غرفه‌ها نیز normalize می‌شوند. اتصال‌های plaintext ورودی بلافاصله با Web Crypto رمز می‌شوند.

PBKDF2 در Worker دقیقاً با سقف Cloudflare یعنی 100,000 iteration اجرا می‌شود. اگر فایل حاوی envelope رمزگذاری‌شدهٔ قدیمی با iteration بیشتر باشد، import به‌جای خطای runtime با پیام سازگاری و HTTP 400 متوقف می‌شود؛ در این حالت از نسخه PHP یک settings export تازه با اتصال‌های قابل انتقال بگیرید و همان فایل را از داشبورد وارد کنید. `VAULT_SECRET` هیچ‌گاه در log یا `/api/debug` برگردانده نمی‌شود.

پیش از migration بزرگ، endpoint `/api/backup` را اجرا و فایل JSON دانلودشده را روی دستگاه خود نگه‌داری کنید. بازیابی از `/api/restore` انجام می‌شود. حالت `/api/backup?persist=true` فقط برای استقرارهای دارای R2 است و در نسخهٔ بدون subscription پیام راهنمای کنترل‌شده برمی‌گرداند.

## API و امنیت

- `GET /health` عمومی است و secret نمایش نمی‌دهد.
- ورود با `ADMIN_TOKEN` فعلاً غیرفعال است و تمام `/api/*` بدون هدر ورود در دسترس‌اند؛ URL Worker را عمومی منتشر نکنید.
- عملیات مخرب همچنان به عبارت تأیید `APPLY` یا `DELETE` نیاز دارند.
- Visual Selector ticket امضاشده و پنج‌دقیقه‌ای دارد؛ HTML مقصد sanitize می‌شود.
- fetch مقصد فقط HTTP/HTTPS عمومی را می‌پذیرد، redirect را دوباره اعتبارسنجی می‌کند و پاسخ محدود دارد.
- مستقیم‌رفتن از طریق SOCKS، custom DNS یا proxy سطح socket در Workers ممکن نیست. حالت `workerUrl` به‌عنوان gateway HTTP هم برای AI و هم scraping فهرست/جزئیات عملیاتی است؛ modeهای غیرقابل‌اجرا با خطای روشن رد می‌شوند.

endpointهای تشخیصی مهم:

```text
GET  /api/status
GET  /api/selftest
GET  /api/debug
GET  /api/parity
GET  /api/jobs
POST /api/queue-watchdog
POST /api/source-test
```

## Cron، Queue و بازیابی

Cron هر دقیقه:

- jobهای running راکد را با watchdog می‌بندد؛
- profileهای موعدرسیده را enqueue می‌کند؛
- jobهای queued بدون پیام را recover می‌کند؛
- autoreply و digest زمان‌بندی‌شده را اجرا می‌کند.

Scrape در مرز هر chunk، شماره صفحه، URL بعدی، محصولات page، offset و source keyهای دیده‌شده را checkpoint می‌کند. `next_selector` واقعاً href لینک بعد را از HTML می‌گیرد. retirement فقط پس از پایان موفق پیمایش اجرا می‌شود. خطای هر مقصد برای هر محصول ثبت می‌شود و مقصد/محصول بعدی ادامه پیدا می‌کند.

## Direct Upload و به‌روزرسانی

`deploy-worker.ts` فقط `scraper4.worker.js` را upload می‌کند و bindingهای موجود را با `keep_bindings` نگه می‌دارد. این مسیر برای **به‌روزرسانی کد پس از bootstrap موفق** است؛ نصب نخست باید از Workers Builds و `npm run worker:deploy` انجام شود، زیرا Direct Upload به‌تنهایی resourceهای account-level یا migrationها را provision نمی‌کند.

هر بار پس از تغییر source، bundle tracked با `npm run worker:build` بازسازی می‌شود.

## نسخه و rollback

نسخه‌ها و deploymentها از تب **Deployments** خود Worker در Dashboard دیده می‌شوند و rollback از همان رابط قابل انجام است. برای تغییر schema، migration جدید بسازید؛ migration قبلی را بعد از استفاده در production ویرایش نکنید.

## تازه‌های نسخهٔ ۱.۹۶.۰

- **پیش‌نمایش هماهنگ‌سازی دیگر متن خام نیست؛ یک جدول ماتریسی رنگی است.** هر سطر یک محصول و هر ستون یک مقصد (ووکامرس و تک‌تک غرفه‌های باسلام) است؛ رنگ هر سلول وضعیت همان محصول در همان مقصد را می‌گوید: سبز = هماهنگ، نارنجی = اختلاف قیمت، آبی = در مقصد نیست، قرمز = فقط در مقصد، بنفش = بدون قیمت مبدأ، خاکستری = به آن مقصد ارسال نمی‌شود. علاوه بر رنگ، هر سلول نشانه و برچسب فارسی دارد و با نگه‌داشتن ماوس جزئیات کامل را نشان می‌دهد. پیش‌نمایش هیچ تغییری ثبت نمی‌کند؛ پس از اجرا، همین جدول با وضعیت واقعی دوباره رسم می‌شود.

## تازه‌های نسخهٔ ۱.۹۵.۰

- **رفع «۰ از ۰» در اجرای واقعی پروفایل.** دو علت مستقل: الف) وقتی تعداد صفحات ۰ (خودکار) بود، اجراگر Node هیچ صفحه‌ای را نمی‌پیمود در حالی که Worker تا ۱۰۰ صفحه می‌رفت؛ ب) اگر سلکتور لینک روی تصویر محصول تنظیم شده بود، آدرس محصول خالی می‌ماند و همهٔ محصولات دور ریخته می‌شدند. حالا لینک از خود عنصر، والد آن، یا نزدیک‌ترین `a[href]` داخل کارت پیدا می‌شود. به همین دلیل بود که عیب‌یابی ۲۰ محصول می‌دید ولی اجرا هیچ محصولی ذخیره نمی‌کرد.
- **دکمهٔ جدول مغایرت در محیط‌های غیرابری کار می‌کند.** پیش‌تر روی Termux/VPS/Render خطای `D1 binding DB is not configured` می‌داد، چون کد مشترک به لایهٔ دیتابیس Cloudflare دست می‌زد. اکنون هر اجراگر از دیتابیس خودش می‌خواند.
- **مغایرت‌گیری یکپارچه.** یک جدول پیشرفته که همهٔ پروفایل‌ها را هم‌زمان با ووکامرس و تک‌تک غرفه‌های باسلام مقایسه می‌کند: قیمت (پس از اعمال درصد تعدیل همان غرفه و تبدیل به ریال) و بود/نبود محصول. دکمهٔ «پیش‌نمایش» فهرست اقدامات را بدون تغییر نشان می‌دهد و دکمهٔ «اجرا و هماهنگ‌سازی» قیمت‌ها را اصلاح و محصولات جاافتاده را منتشر می‌کند. محصولی که فقط در مقصد است هرگز خودکار حذف نمی‌شود.
- **موتور `cheerio` در همهٔ فهرست‌های کشویی.** در ۱.۹۴.۰ فقط فهرست تنظیمات اصلاح شده بود و فهرست صفحهٔ شروع همچنان موتور ذخیره‌شده را به `auto` برمی‌گرداند.
- **به‌روزرسانی خودکار در دیپلویر واقعاً انجام می‌شود.** دکمهٔ «اسکن فوری» فقط جدول را تازه می‌کرد، و فایل‌های ساخته‌شده (`scraper4.worker.js`، `scraper4.ts`، `package-lock.json`) به‌اشتباه «کار دستی کاربر» شمرده می‌شدند و به‌روزرسانی خودکار را برای همیشه متوقف می‌کردند.

## تازه‌های نسخهٔ ۱.۹۴.۰

- **موتور `cheerio` در فهرست موتورها.** آزمون سرعت سه‌صفحه‌ای این موتور را می‌سنجید و به‌عنوان برنده در پروفایل ذخیره می‌کرد، اما در فهرست کشویی نبود و هنگام ذخیرهٔ بعدی بی‌صدا به `auto` برمی‌گشت. اکنون در هر دو اجراگر (Node و Cloudflare Worker) هم انتخاب‌شدنی است و هم ماندگار.
- **دکمهٔ «همگام‌سازی دستی» در صفحهٔ شروع.** یک کلیک: استخراج فهرست ← استخراج جزئیات (اگر تنظیم شده باشد) ← ارسال به ووکامرس و همهٔ غرفه‌های فعال باسلام. اگر هیچ مقصدی فعال نباشد، مثل قبل فقط استخراج انجام می‌شود.
- **«توضیح‌ساز» در بخش هوش مصنوعی.** به‌صورت پیش‌فرض روشن است و با **مدل مستر** فقط فیلدهای خالی محصول (توضیح کوتاه، توضیح بلند و تنوع‌ها) را پر می‌کند. متنی که واقعاً از سایت مبدأ استخراج شده هرگز بازنویسی نمی‌شود و هیچ عکسی ساخته نمی‌شود؛ گالری فقط از تصاویر واقعی همان صفحه پر می‌شود. خطای هوش مصنوعی هیچ‌وقت باعث شکست استخراج نمی‌شود.
- متغیر اختیاری `AI_DESCRIPTION_CONCURRENCY` (پیش‌فرض ۲) تعداد محصولات هم‌زمان در توضیح‌ساز را تعیین می‌کند.

## تازه‌های نسخهٔ ۱.۹۷.۰

- **«پیشنهاد خودکار سلکتورها» حالا آخرین راه نجات است.** پیش‌تر فقط زمانی اجرا می‌شد که یکی از موتورها از قبل محصولی پیدا کرده بود، یعنی دقیقاً در بدترین حالت (صفر محصول) بی‌فایده بود. حالا در سه حالت خودکار اجرا می‌شود: سلکتورهای فهرست خالی باشند، اتصال برقرار شود ولی صفر محصول استخراج شود، یا موتور استخراج هیچ کارتی پیدا نکند. سلکتورها دوباره کشف می‌شوند و همان صفحه یک‌بار دیگر استخراج می‌شود.
- **همین مکانیزم در مرحلهٔ جزئیات.** اگر سلکتورهای جزئیات روی یک محصول واقعی هیچ فیلدی را پر نکنند، دوباره کشف و آزمایش می‌شوند تا محصولات با توضیحات خالی ذخیره نشوند.
- **در تب سلکتورها و تب سلکتورهای جزئیات:** دکمه‌های آزمایش، وقتی هیچ فیلدی جواب ندهد، خودشان پیشنهاد خودکار را اجرا می‌کنند.
- هر نجات در هر اجرا فقط یک‌بار انجام می‌شود تا حلقهٔ بی‌پایان ایجاد نشود؛ روی Cloudflare این وضعیت در checkpoint ذخیره می‌شود و بعد از resume تکرار نمی‌شود.
- **به‌روزرسانی خودکار از گیت‌هاب دیگر دستی نیست.** نصب‌کنندهٔ محلی فایل‌های ردیابی‌نشده (`data/`، `storage/`، یادداشت‌های شخصی) را تغییر محلی حساب می‌کرد و متوقف می‌شد؛ حالا فقط تغییرات فایل‌های ردیابی‌شده شمرده می‌شود و یک `.gitignore` ریشه اضافه شده است.

## تازه‌های نسخهٔ ۱.۹۸.۰

- **ضریب تعدیل قیمت برای ووکامرس:** پیش‌تر فقط غرفه‌های اضافی باسلام فیلد «تغییر قیمت ٪» داشتند و ووکامرس و غرفهٔ پیش‌فرض باسلام ثابت روی صفر بودند. حالا هر دو فیلد مخصوص خود را دارند. این ضریب هم روی قیمت ارسالی به مقصد (شامل تنوع‌ها) اعمال می‌شود و هم در مغایرت‌گیری و پیش‌نمایش هماهنگ‌سازی به‌عنوان «قیمت صحیح» در نظر گرفته می‌شود.
- **دکمهٔ پیش‌نمایش هماهنگ‌سازی:** چون داخل یک درخواست اجرا می‌شد، هیچ ردیفی در مدیر وظایف ساخته نمی‌شد و دکمه مرده به نظر می‌رسید. حالا پیام «در حال خواندن مقصدها…» و یک ردیف زنده در مدیر وظایف نمایش داده می‌شود.
- **نتیجهٔ خالی، دلیل مشخص:** «هیچ مقصدی تنظیم نشده»، «هنوز محصولی استخراج نشده» یا «همه‌چیز هماهنگ است».
- **گزارش تغییرات کوتاه شد:** فقط ۱۲ مورد آخر باز است و بقیه در بخش جمع‌شدهٔ «نمایش همهٔ تغییرات قدیمی‌تر» قرار دارند تا رسیدن به بخش‌های پایین منو سریع باشد.

## تازه‌های نسخهٔ ۱.۹۹.۰

- **Worker واسط برای صفحات مبدأ هم به‌کار می‌رود:** اگر در «روش اتصال» آدرس Worker را وارد کنید، دیگر لازم نیست در تک‌تک پروفایل‌ها تیک «اتصال غیرمستقیم» را بزنید؛ استخراج هم از همان مسیر عبور می‌کند. (در محیط Cloudflare پروکسی HTTP در دسترس نیست؛ پیام خطا این را صریح می‌گوید.)
- **انتخاب دستی موتور استخراج محترم است** و اگر چیزی پیدا نکند، موتورهای دیگر (شامل `htmlrewriter`) فال‌بک می‌شوند؛ این همان اختلافی بود که بین «تست سه صفحه‌ای» و استخراج واقعی دیده می‌شد.
- **استخراج جزئیات:** سلکتوریابی خودکار قبل از توضیح‌ساز هوشمند اجرا می‌شود.
- **پیش‌نمایش هماهنگ‌سازی تمام‌صفحه** شد و ستون «پروفایل» در موبایل دیگر خالی نیست.

## تازه‌های نسخهٔ ۱.۱۰۰.۰

- **مغایرت‌گیری و هماهنگ‌سازی فقط برای محصولات دارای پسوند «(کد ایکس)»:** ایکس هر حرف یا عددی می‌تواند باشد — «(کد ۱۲)»، «(کد A5)»، «(کد:ب۳)» و «#77» همگی معتبرند. عنوان‌های بدون این پسوند عنوانِ پایه/پیش‌نویس در نظر گرفته می‌شوند و نه مقایسه و نه به ووکامرس/باسلام ارسال می‌شوند. تعداد نادیده‌گرفته‌شده‌ها زیر جدول («… بدون پسوند کد») نمایش داده می‌شود. فرمت‌ها از همان تنظیم «فرمت پسوند کد» در منوی حذف تکراری‌ها خوانده می‌شود.
- **ستون «تکراری»:** تعداد محصولاتی که با نادیده‌گرفتن پسوند کد عنوان یکسان دارند؛ گروه‌های بزرگ‌تر از یک با رنگ زرد مشخص می‌شوند.
- **جدول تست مدل‌های هوش مصنوعی با ریفرش صفحه باز نمی‌شود** و فقط پس از پایان اجرایی که همان تب دیده، ظاهر می‌گردد.

## نسخهٔ ۱.۱۰۱.۰ — ارسال به همهٔ غرفه‌ها، شمارنده‌های کلیک‌شدنی و حذف تکراری‌ها در همهٔ مقصدها

- **ارسال باسلام واقعاً به همهٔ غرفه‌ها می‌رسد.** حلقهٔ چندغرفه‌ای وجود داشت، اما کل حلقه داخل یک
  `try/catch` بود: اگر غرفهٔ دوم از سه غرفه خطا می‌داد، ارسال رها می‌شد و موفقیت غرفهٔ اول هم هرگز
  گزارش نمی‌شد. حالا هر غرفه جداگانه گزارش می‌شود و خطای یکی جلوی بقیه را نمی‌گیرد.
- **SDK رسمی باسلام حالا واقعاً استفاده می‌شود.** باسلام SDK را فقط برای **پایتون** منتشر کرده
  (`pip install basalam-sdk`) و هیچ بستهٔ npm ندارد؛ به همین دلیل مسیر «اول SDK» همیشه شکست می‌خورد و
  بی‌صدا به REST برمی‌گشت. حالا SDK واقعی از طریق `scripts/basalam-sdk-bridge.py` (با `python3`) اجرا
  می‌شود و اگر پایتون یا SDK نبود، خودکار به API برمی‌گردد. مفسر با `BASALAM_PYTHON` و مهلت با
  `BASALAM_SDK_TIMEOUT_MS` (پیش‌فرض ۴۵۰۰۰) قابل تنظیم است.
- **شمارنده‌ها کلیک‌شدنی‌اند و جزئیات واقعی دارند.** با کلیک روی شمارندهٔ هر کار، نام محصول، قیمت آن و
  نام مقصد/غرفه دیده می‌شود و روی شمارندهٔ خطاها متن کامل خطا نمایش داده می‌شود. نسخهٔ نود اصلاً
  جزئیاتی ثبت نمی‌کرد و این پنجره بیرون از کلودفلر همیشه خالی بود؛ حالا هر دو نسخه یکسان ثبت می‌کنند.
- **حذف تکراری‌ها در همهٔ مقصدها.** در بخش مغایرت‌گیری دو دکمهٔ «پیش‌نمایش تکراری‌های مقصد» و
  «حذف تکراری‌ها در همهٔ مقصدها» اضافه شد. عنوان‌هایی که پس از حذف پسوند «(کد ایکس)» یکسان می‌شوند یک
  گروه تکراری‌اند و به‌صورت پیش‌فرض **گران‌ترین** نسخه نگه داشته و بقیه حذف می‌شوند (ووکامرس حذف
  واقعی، باسلام بایگانی ۴۱۸۴ چون API آن حذف دائمی ندارد). اول پیش‌نمایش، بعد تأیید. محصولات محلی
  دست‌نخورده می‌مانند.
- **رفع اشکال: گروه‌بندی تکراری‌ها پسوند عمومی کد را نادیده می‌گرفت.** تابع `dedupKey` فقط قالب‌های
  *تنظیم‌شده* را حذف می‌کرد، بنابراین فروشگاهی پر از «کیف چرم (کد ۱۱)» و «(کد ۱۲)» هیچ گروهی تولید
  نمی‌کرد و حذف تکراری بی‌صدا هیچ کاری نمی‌کرد.
- **رفع اشکال: حذف تکراری سمت سرور اصلاً در نسخهٔ نود نبود.** هر چهار مسیر `dedup-runs` فقط روی
  کلودفلر وجود داشتند و این دکمه‌ها روی ترموکس، VPS، Render و Codespaces بی‌اثر بودند.
- راه‌اندازی ترموکس حالا SDK را هم نصب می‌کند: `pip install basalam-sdk`.

## نسخهٔ ۱.۱۰۲.۰ — رفع خطای HTTP 400 باسلام، نتایج تک‌ستونه با مودال محصول و پرکردن خودکار تنظیمات

- **خطای `HTTP 400` باسلام که جلوی هر ارسال واقعی را گرفته بود برطرف شد.** پیام‌های
  `photo: Input should be a valid integer` و `status: Field required` از سه فیلد اشتباه می‌آمدند:
  - `photo` باید **شناسهٔ عددی فایل آپلودشده در `/v1/files`** باشد، نه آدرس تصویر. حالا تصاویر ابتدا
    آپلود می‌شوند (`file_type=product.photo`) و فقط شناسهٔ عددی آن‌ها در `photo` و `photos[]` ارسال
    می‌شود. اگر آپلود شکست بخورد، محصول بدون عکس ارسال می‌شود تا کل ارسال از دست نرود.
  - فیلد `status` **اجباری** است و اکنون با مقدار `2976` (منتشرشده) ارسال می‌شود.
  - نام درست فیلد قیمت **`primary_price`** است، نه `price`.
  این موارد با `ProductRequestSchema` رسمی نسخهٔ ۱.۲.۰ بستهٔ `basalam-sdk` راستی‌آزمایی شدند.
- **بخش نتایج تک‌ستونه شد.** هر ردیف تصویر، نام محصول همراه پسوند «(کد ایکس)»، **قیمت پایه با خط وسط**
  و **قیمت نهایی به تومان** برای غرفهٔ پیش‌فرض باسلام را نشان می‌دهد.
- **با کلیک روی هر محصول، مودال آن باز می‌شود**: گالری تصاویر، جدول قیمت نهایی برای **همهٔ** مقصدها
  (ووکامرس و تک‌تک غرفه‌های باسلام، همراه معادل ریال)، جزئیات محصول، تنوع‌ها و توضیحات کامل.
- **پرکردن خودکار تنظیمات باسلام.** با وارد کردن توکن و زدن دکمهٔ تست، شناسهٔ غرفه و روزهای
  آماده‌سازی از `users/me` استعلام و خودکار پر می‌شوند؛ تست هر غرفهٔ اضافه، شناسه و نام همان غرفه را
  پر می‌کند. نسخهٔ نود تا امروز فقط `/categories` را صدا می‌زد و هیچ مشخصاتی برنمی‌گرداند.

## نسخهٔ ۱.۱۰۳.۰ — رفع خطای ۴۰۴ پراکسی هوش مصنوعی و بازگشت جدول ماتریسی مغایرت‌گیری

- **رفع اشکال: آدرس پراکسی بدون //:https باعث خطای ۴۰۴ همهٔ مدل‌ها می‌شد.** نوشتن
  `proxy.example.workers.dev` (همان‌طور که کلودفلر نشان می‌دهد) یک آدرس **نسبی** می‌ساخت و روی دامنهٔ
  خود اسکرپر حل می‌شد؛ یعنی مسیری که وجود ندارد و نتیجه‌اش ۴۰۴ برای همهٔ مدل‌ها بود، در حالی که
  اتصال مستقیم درست کار می‌کرد. حالا آدرس پراکسی در **هر دو نسخه** (ورکر و نود) و برای هوش مصنوعی،
  ووکامرس و استخراج خودکار اصلاح می‌شود. دو فیلد آدرس هم دیگر نام میزبان بدون پیشوند را قبول می‌کنند.
- **فایل جدید `scripts/ai-proxy-worker.js`** — یک Worker آمادهٔ کلودفلر. حتی با آدرس درست، اگر ورکر
  واسط قرارداد موردانتظار را پیاده نکرده باشد باز هم ۴۰۴ می‌گیرید؛ این فایل آن را پیاده می‌کند:
  پارامتر `?url=`، هدرهای `x-scraper-target` و `x-target-url` و حالت مسیری را می‌پذیرد،
  متد/بدنه/Authorization را دست‌نخورده عبور می‌دهد، به preflight پاسخ می‌دهد، مسیر `/health` دارد و
  با فهرست `ALLOWED_HOSTS` جلوی سوءاستفاده به‌عنوان رله باز را می‌گیرد.
- **پیش‌نمایش مغایرت‌گیری دوباره جدول ماتریسی را نشان می‌دهد.** پیش‌نمایش فقط تراشه‌های شمارش را
  نشان می‌داد و جدول کامل تنها بعد از «اجرا» می‌آمد؛ حالا هر دو یک جدول (محصول × مقصد) دارند.
- **رفع اشکال: وقتی همهٔ مقصدها خطا می‌دادند، پیام «همه‌چیز هماهنگ است» نشان داده می‌شد.** سه خطای
  ۴۰۱ به پیام سبز «همهٔ مقصدها با مبدأ یکسان‌اند» ختم می‌شد. حالا هشدار قرمز «هیچ مقصدی پاسخ نداد»
  همراه فهرست خطاها می‌آید و تا وقتی مقصدی خطا دارد پیام سبز نمایش داده نمی‌شود.

## نسخهٔ ۱.۱۰۴.۰ — رفع خطای «invalid authorization header» باسلام

- **خطای `HTTP 401: invalid authorization header` در ارسال باسلام برطرف شد.** اگر توکن را همان‌طور
  که در مستندات نوشته شده کپی می‌کردید («Bearer eyJ…»)، همان رشته عیناً ذخیره می‌شد و درخواست با
  هدر `Authorization: Bearer Bearer eyJ…` (دو بار Bearer) ارسال می‌شد که باسلام آن را نامعتبر
  می‌داند. حالا توکن هم هنگام ذخیره و هم هنگام خواندن پاک‌سازی می‌شود:
  - پیشوندهای `Bearer` و `Token` و `:Authorization` حذف می‌شوند،
  - گیومه‌های دور توکن و فاصله‌های ابتدا و انتها پاک می‌شوند،
  - نویسه‌های نامرئی (نیم‌فاصله، علامت‌های راست‌به‌چپ، فاصلهٔ بدون شکست، گیومه‌های فارسی) حذف
    می‌شوند؛ این نویسه‌ها اصلاً در هدر HTTP مجاز نیستند و باعث خطا یا رد شدن درخواست می‌شدند.
- **توکن‌هایی که قبلاً اشتباه ذخیره شده‌اند، هنگام بارگذاری خودکار اصلاح می‌شوند** و نیازی به وارد
  کردن دوباره نیست.
- همین پاک‌سازی برای **غرفه‌های اضافهٔ باسلام** و متغیر محیطی **`BASALAM_TOKEN`** هم اعمال می‌شود.
- متن خطای ۴۰۱ حالا راه‌حل را توضیح می‌دهد و کنار فیلد توکن هم نوشته شده که فقط خود توکن، بدون
  واژهٔ Bearer، وارد شود.

اگر بعد از این باز هم خطای ۴۰۱ گرفتید، یعنی خود توکن نامعتبر یا منقضی است؛ از پنل توسعه‌دهندگان
باسلام یک توکن دسترسی شخصی تازه با Scopeهای لازم بسازید.

## نسخهٔ ۱.۱۰۵.۰ — تشخیص دقیق علت خطای ۴۰۱ باسلام

- **درستی درخواستی که می‌فرستیم تأیید شد.** با اجرای واقعی `safeFetch` و رهگیری لایهٔ انتقال معلوم شد
  هدر خروجی دقیقاً `Authorization: Bearer <token>` است؛ بدون تکرار Bearer، بدون نویسهٔ اضافه و با
  آدرس درست. پس اگر باز هم `401 invalid authorization header` می‌گیرید، یعنی خودِ توکن رد می‌شود، نه
  قالب هدر.
- **توکن حالا به‌صورت محلی و بدون هیچ درخواست شبکه‌ای بررسی می‌شود.** توکن‌های دسترسی شخصی باسلام
  JWT هستند، بنابراین محتوایشان رمزگشایی و علت واقعی گزارش می‌شود: توکن خالی است، هنوز واژهٔ
  `Bearer` دارد، فاصله یا خط جدید دارد، **منقضی** شده (تاریخ انقضا چاپ می‌شود) یا دسترسی
  **`vendor.product.write`** را ندارد (دسترسی‌های فعلی فهرست می‌شوند).
- این تشخیص هم در متن خطای ارسال و هم در «استعلام جامع باسلام» دیده می‌شود و حتی وقتی باسلام در
  دسترس نیست هم کار می‌کند؛ پیش از این، قطعی شبکه فقط پیام `fetch failed` بدون هیچ اطلاعاتی دربارهٔ
  توکن برمی‌گرداند.

اگر نتیجه بگوید ساختار توکن سالم است ولی باسلام باز هم ۴۰۱ بدهد، یعنی توکن باطل شده یا متعلق به
حساب دیگری است؛ از developers.basalam.com/panel/tokens یک توکن تازه با Scope
`vendor.product.write` بسازید.

## نسخهٔ ۱.۱۰۷.۰ — توضیح خطای ۴۰۱ باسلام وقتی خود توکن سالم به نظر می‌رسد

- **تأیید شد درخواست ما دقیقاً مطابق SDK رسمی است.** بررسی کد `basalam-sdk` نسخهٔ ۱.۲.۰ نشان می‌دهد
  همان مسیر `/v1/vendors/{vendor_id}/products`، همان بدنهٔ JSON و همان هدر
  `Authorization: Bearer <token>` را می‌سازد. پس خطای ۴۰۱ در حالتی که بررسی محلی می‌گوید «ساختار توکن
  سالم است»، مشکل قالب هدر نیست و با بررسی صرفاً محلی هم قابل توضیح نیست.

  از هم جدا می‌شوند:
  - اگر `users/me` هم ۴۰۱ بدهد → توکن باطل یا نامعتبر است؛ توکن تازه بسازید.

- **رفع یک پیام گمراه‌کننده:** توکنی که فهرست دسترسی داخلش نبود، بی‌صدا از بررسی Scope رد می‌شد و

## نسخهٔ ۱.۱۰۸.۰ — فعال شدن «اتصال غیرمستقیم» باسلام، کارت cPanel و تاشو شدن فهرست‌ها

- **رفع اشکال: تیک «اتصال غیرمستقیم» باسلام ذخیره می‌شد ولی هیچ درخواستی آن را نمی‌خواند.** یعنی

  دادند** و ووکامرس هم هم‌زمان خطای `error code: 522` داد. توکن نمی‌تواند باعث ۵۲۲ شود؛ یعنی لبهٔ
  شبکهٔ مقصد ترافیک را رد می‌کرد. باسلام درخواست‌های آمده از رنج دیتاسنتر را پیش از بررسی توکن رد

- در `scripts/ai-proxy-worker.js` میزبان‌های `openapi.basalam.com` و `auth.basalam.com` و

- **کارت «cPanel Shared Hosting»** با دستورهای کامل به بخش نصب اضافه شد و فایل اجرای آن با نام
  `scraper4-install-cpanel.sh` دانلود می‌شود.
- **منو دیگر یک اسکرول بی‌پایان نیست:** فقط تازه‌ترین کارت گزارش تغییرات باز است و ۱۴ مورد قبلی به

- **دستورالعمل نصب هر محیط کشویی شد** و به‌صورت پیش‌فرض بسته می‌ماند؛ دکمه‌های کپی و دانلود سر جای

## نسخهٔ ۱.۱۰۹.۰ — بازگشت جدول کامل مغایرت‌گیری وقتی یک مقصد خطا می‌دهد

- **رفع بازگشت‌پذیری‌ای که باعث می‌شد جدول کامل مقایسه ناپدید شود.** در حلقهٔ مغایرت‌گیری، مقصدی که

  جدول داده‌ای برای رسم نداشت و محافظ نسخهٔ ۱.۱۰۳.۰ آن را با یک پیام خطای ساده جایگزین می‌کرد؛ به
  همین دلیل جدولی که قبلاً می‌دیدید دیگر نمی‌آمد.
  حالا مقصدی که پاسخ نمی‌دهد هم برای هر محصول یک خانه می‌سازد با وضعیت تازهٔ **«مقصد پاسخ نداد»**
  (نشانهٔ ⛔ و رنگ صورتی). جدول کامل دوباره رسم می‌شود — همهٔ سطرهای محصول و همهٔ ستون‌های مقصد — و
  فهرست خطای هر مقصد بالای آن می‌آید. خانه‌های بی‌پاسخ بالاترین اولویت مرتب‌سازی را دارند. اصلاح در

## نسخهٔ ۱.۱۱۰.۰ — تطبیق ارسال باسلام با کد مرجع PHP (نسخهٔ ۱۰.۹۱)

فایل مرجع از مخزن `fazilatma/code` خوانده شد و دو تفاوت تعیین‌کننده پیدا شد که هر دو رفع شدند:

- **محصول باید ابتدا به‌صورت پیش‌نویس ساخته شود.** تابع `bslSendProduct()` هر محصول را با
  `status = 3790` (منتشرنشده) می‌سازد، در حالی که ما مستقیم `2976` (منتشرشده) می‌فرستادیم.
- **درخواست ساخت نباید عکس داشته باشد.** در پیلود PHP هیچ کلید `photo` یا `photos` وجود ندارد:
  فقط `name`، `brief`، `description`، `primary_price`، `stock`، `preparation_days`، `weight`،
  `package_weight`، `is_wholesale`، `category_id`، `status` و در صورت وجود `sku`. عکس‌ها به
  `/files` آپلود می‌شوند و **بعداً** همراه `status = 2976` در یک `PATCH` جداگانه به محصول وصل می‌شوند.

حالا ارسال ما دقیقاً همین دو مرحله را انجام می‌دهد: ساخت پیش‌نویس بدون عکس، سپس PATCH برای انتشار
همراه شناسه‌های عکس. اگر مرحلهٔ دوم خطا بدهد محصول از دست نمی‌رود و همگام‌سازی بعدی کاملش می‌کند.

همچنین از روی همین مرجع تأیید شد که هدر احراز هویت PHP دقیقاً `Authorization: Bearer <token>` است؛
یعنی قالب هدر ما از ابتدا درست بوده است.

## نسخهٔ ۱.۱۱۱.۰ — دیگر خودمان را مرورگر جا نمی‌زنیم (علت واقعی ۴۰۱ و ۵۲۲)

مقایسهٔ لایهٔ HTTP ما با کد مرجع PHP علت را نشان داد. تابع `bslCurlOpts()` دقیقاً سه هدر می‌فرستد:

```
Accept: application/json
Authorization: Bearer <token>
Content-Type: application/json
```

ما **پنج** هدر می‌فرستادیم، از جمله یک `user-agent` جعلیِ کروم دسکتاپ و `accept-language` فارسی.
فرستادن User-Agent مرورگر به یک API، بدون بقیهٔ نشانه‌های مرورگر، الگوی شناخته‌شدهٔ فایروال‌هاست.
لبهٔ شبکه درخواست را **پیش از خواندن توکن** رد می‌کند و آن را `invalid authorization header` گزارش
می‌دهد؛ به همین دلیل:

- مسیر فقط‌خواندنی `users/me` هم ۴۰۱ می‌داد،
- دو توکن سالم و متفاوت هم‌زمان رد می‌شدند،
- و ووکامرس در همان اجرا `error code: 522` می‌داد.

حالا همهٔ فراخوانی‌های API در هر دو نسخه فقط هدرهای خودشان را می‌فرستند: باسلام (مستقیم و از راه
پراکسی) و مسیر REST ووکامرس. استخراج صفحات فروشگاه همچنان هدرهای مرورگر را دارد، چون بعضی سایت‌ها
بدون آن صفحهٔ ناقص یا صفحهٔ چالش می‌دهند؛ این دو مسیر حالا با پرچم صریح و نوع‌دار `apiMode` از هم
جدا شده‌اند.

## نسخهٔ ۱.۱۱۲.۰ — ابزار عیب‌یاب باسلام برای اجرا روی همان دستگاهی که خطا می‌دهد

خطای ۴۰۱ در محیط ساخت قابل بازتولید نیست (از اینجا مسیری به باسلام وجود ندارد)، بنابراین به‌جای
حدس زدن دوباره، فایل `scripts/basalam-doctor.mjs` اضافه شد که **روی همان دستگاه معیوب** اجرا
می‌شود و دقیقاً می‌گوید باسلام چه پاسخی می‌دهد.

```bash
node scripts/basalam-doctor.mjs <توکن>
# یا بگذارید توکن ذخیره‌شده را از برنامهٔ در حال اجرا بخواند:
SCRAPER_URL=http://127.0.0.1:3000 ADMIN_TOKEN=xxx node scripts/basalam-doctor.mjs
```

همان توکن را به چهار شکل می‌فرستد و وضعیت، بدنه و هدرهای لبه را چاپ می‌کند:

| آزمون | هدرها | چه چیزی را ثابت می‌کند |
| --- | --- | --- |
| الف | Accept و Authorization و Content-Type (دقیقاً مثل `scraper4.php`) | وضعیت توکن روی یک درخواست تمیز |
| ب | به‌علاوهٔ `user-agent` و `accept-language` مرورگر | آیا فایروال، ظاهرِ مرورگر را رد می‌کند |
| ج | فقط Authorization | آیا هدر اضافه‌ای اثر دارد |
| د | مسیر `vendors/{id}/products` | مشکل احراز هویت است یا دسترسی/غرفه |

اگر «الف» کد ۲۰۰ بدهد، توکن سالم است و مشکل در خود برنامه است؛ اگر هر سهٔ الف و ب و ج ۴۰۱ بدهند،
خودِ توکن رد می‌شود. توکن هرگز چاپ نمی‌شود — فقط طول، ساختار، تاریخ انقضا، دسترسی‌ها و یک اثرانگشت
کوتاه و برگشت‌ناپذیر؛ پس خروجی را می‌توان با خیال راحت به اشتراک گذاشت.

## نسخهٔ ۱.۱۱۳.۰ — درخواست‌های مقصد دیگر از پراکسیِ استخراج عبور نمی‌کنند (علت واقعی ۴۰۱)

خروجی عیب‌یاب روی دستگاه معیوب موضوع را قطعی کرد: **هر چهار آزمون کد ۲۰۰ گرفتند** — توکن تا ۲۰۲۷
معتبر، هر ۱۵ دسترسی موجود و فهرست محصولات غرفهٔ ۷۳۵۷۰۳ خوانده شد — در حالی که خود برنامه باز ۴۰۱
می‌گرفت. پس مشکل هرگز از توکن نبود.

در نسخهٔ نود، `safeFetch()` تنظیمات `sourceNetwork` را **بدون هیچ شرطی** روی همهٔ درخواست‌ها اعمال
می‌کرد. آن تنظیم مربوط به «اتصال به سایت مبدأ» برای **استخراج** است و از `ai.network` پر می‌شود.
چون روش اتصال هوش مصنوعی روی **Worker** بود، درخواست‌های احرازهویت‌شدهٔ باسلام و ووکامرس هم از همان
Worker عبور می‌کردند — و آن Worker هدر `Authorization` را منتقل نمی‌کند. بنابراین باسلام درخواستی
بدون توکن می‌دید و `invalid authorization header` می‌داد، و ووکامرس در همان اجرا `522`.

حالا مقصدها مسیر خودشان را دارند:

- **باسلام** از تیک «اتصال غیرمستقیم» خودش پیروی می‌کند: روشن → Worker، خاموش → مستقیم.
- **REST ووکامرس** مستقیم می‌رود.
- **استخراج** مثل قبل از پراکسی استفاده می‌کند.

## نسخهٔ ۱.۱۱۴.۰ — رفع خطای ۴۲۲ «شناسه تصویر الزامی است» (اصلاح اشتباه نسخهٔ ۱.۱۱۰.۰)

خطای ۴۰۱ برطرف شد و احراز هویت کار می‌کند. خطای بعدی اشتباهِ من بود.

در نسخهٔ ۱.۱۱۰.۰ تابع `bslSendProduct()` را خواندم — که مخصوص **غرفه‌های اضافه** است — و اشتباه
نتیجه گرفتم که فیلد `photo` نباید هنگام ساخت ارسال شود. **مسیر اصلی ارسال** در همان فایل PHP دقیقاً
برعکس عمل می‌کند: `'photo' => $pid` و `'photos' => [...]` را در همان درخواست ساخت می‌فرستد و باسلام
هم آن را اجباری می‌داند.

قانون واقعی `scraper4.php`:

- ابتدا تصاویر آپلود می‌شوند؛
- اگر آپلود موفق بود، `photo` و `photos` ارسال می‌شوند و اگر توضیح کوتاه و توضیح کامل هر دو دست‌کم
  ۳ نویسه باشند، وضعیت **۲۹۷۶** (منتشرشده) می‌شود؛
- در غیر این صورت وضعیت **۳۷۹۰** (پیش‌نویس) است تا محصول دست‌کم ثبت شود و رد نشود.

اکنون دقیقاً همین پیاده شده و درخواست PATCH اضافیِ نسخهٔ ۱.۱۱۰.۰ حذف شد.

**خطای آپلود تصویر دیگر بی‌صدا نیست.** پیش‌تر با یک `catch` خالی نادیده گرفته می‌شد و به همین دلیل
خطای ۴۲۲ بدون هیچ توضیحی می‌آمد. حالا اگر ۴۲۲ به `photo` اشاره کند، نام تصویر و علت دقیق نوشته
می‌شود — مثلاً «علت: a.jpg: HTTP 413» — یا صریح گفته می‌شود که محصول اصلاً تصویری ندارد.

## نسخهٔ ۱.۱۱۷.۰ — خطای ۱۰۴۲ کلودفلر روی پراکسی هوش مصنوعی و سهمیهٔ اجرای Worker

- **علت `error code: 1042` مشخص شد.** کلودفلر اجازه نمی‌دهد یک Worker، Worker دیگری از **همان حساب**
  را صدا بزند؛ لبهٔ شبکه **پیش از اجرای پراکسی** کد ۴۰۴ برمی‌گرداند و به همین دلیل عیب‌یاب می‌گفت
  «پراکسی پاسخ داد ولی درخواست را به مقصد نرساند». راه‌حل رسمی یعنی
  `compatibility_flags = ["global_fetch_strictly_public"]` به `wrangler.toml` اضافه شد.
  **همین پرچم را باید در پنل کلودفلر برای هر دو Worker** (این اسکرپر و پراکسی) فعال کنید:
  *Settings → Runtime → Compatibility flags* و سپس Deploy. راه جایگزین: پراکسی را روی حساب دیگری
  مستقر کنید یا برایش دامنهٔ اختصاصی تعریف کنید. عیب‌یاب هوش مصنوعی حالا خطای ۱۰۴۲ را می‌شناسد و
  دقیقاً همین مراحل را نشان می‌دهد.
- **نوار سهمیه حالا عملیات هوش مصنوعی را هم پوشش می‌دهد.** تماس با مدل‌ها چیزی در D1 نمی‌نویسد و به
  همین دلیل دیده نمی‌شد. دو ردیف اضافه شد: تعداد اجراهای Worker در روز (سقف ۱۰۰٬۰۰۰) و **بیشینهٔ
  درخواست بیرونی در یک اجرا** (سقف ۵۰ در پلن رایگان) که سقف واقعیِ تست مدل‌هاست.

## نسخهٔ ۱.۱۱۸.۰ — اصلاح راهنمای ۱۰۴۲ برای ترموکس و حذف دانلود بی‌دلیل صفحات جزئیات

- **رفع اشکال: راهنمای `error code: 1042` مخصوص کلودفلر بود ولی فقط در نسخهٔ نود دیده می‌شود.**
  آن عیب‌یاب در `render-src/ai.ts` است که روی ترموکس، VPS و سی‌پنل اجرا می‌شود، نه روی کلودفلر. یک
  کلاینت ساده Node اصلاً Worker نیست، پس قانون «یک Worker نمی‌تواند Worker دیگری از همان حساب را صدا
  بزند» به درخواست شما ربطی ندارد. دریافت ۱۰۴۲ در این محیط معنای دیگری دارد: **روی آن آدرس هیچ
  Workerِ فعالی مستقر نیست** و پاسخ را خودِ لبهٔ کلودفلر داده است. حالا پیام همین را می‌گوید و
  راه‌حل درست را نشان می‌دهد: فایل `scripts/ai-proxy-worker.js` را Deploy کنید و مسیر `/health` آن
  را بررسی کنید. پرچم `global_fetch_strictly_public` فقط به‌عنوان نکتهٔ تکمیلی برای کسانی می‌ماند که
  پراکسی را از داخل یک Worker دیگر صدا می‌زنند.
- **رفع اشکال: مرحلهٔ جزئیات حتی بدون هیچ سلکتور جزئیاتی، صفحهٔ تک‌تک محصولات را دانلود می‌کرد.**
  چیزی پر نمی‌شد، پس آن صدها درخواست کاملاً بی‌فایده بودند. حالا اگر سلکتوری تنظیم نشده باشد، اول
  خودکار کشف می‌شود؛ اگر باز هم چیزی پیدا نشد، این مرحله رد می‌شود و همین در گزارش نوشته می‌شود.
  در پایان هم تعداد محصولاتی که جزئیاتشان استخراج شد گزارش می‌گردد. در هر دو نسخه اعمال شد.

## نسخهٔ ۱.۱۱۹.۰ — آدرس پراکسی هوش مصنوعی دوبار بسته‌بندی می‌شد (علت واقعی ۱۰۴۲ و ۴۰۴)

پراکسی شما هیچ اشکالی نداشت؛ اشکال از ما بود.

تابع `networkFetch()` آدرس مقصد را داخل پراکسی می‌گذاشت — `proxy/?url=https://api.openai.com/…` —
و بعد نتیجه را به `safeFetch()` می‌داد، و آن هم **دوباره** همان تنظیم «روش اتصال» را اعمال می‌کرد و
آدرس را **بار دوم** داخل پراکسی می‌گذاشت. یعنی از پراکسی می‌خواستیم خودش را fetch کند؛ و این دقیقاً
همان «یک Worker، Worker دیگری از همان حساب را صدا بزند» است که کلودفلر با `error code: 1042` رد
می‌کند و برای همهٔ مدل‌ها به‌صورت ۴۰۴ برمی‌گشت.

حالا آدرسی که یک‌بار بسته‌بندی شده دیگر بار دوم از مسیر پراکسی عبور نمی‌کند (`directRoute`)، هم در
تماس واقعی با مدل‌ها و هم در عیب‌یاب. راستی‌آزمایی شد: آدرس دقیقاً یک‌بار بسته‌بندی می‌شود.

راهنمای نسخهٔ قبل دربارهٔ فعال کردن `global_fetch_strictly_public` پس گرفته می‌شود؛ مشکل هرگز از
تنظیمات کلودفلر شما نبود.

## نسخهٔ ۱.۱۲۰.۰ — گم شدن هزاران محصول در نتایج و نادیده گرفتن محصولات بدون قیمت

- **رفع اشکال: ۱۲۰۰ محصول استخراج می‌شد ولی فقط حدود ۲۰ مورد ذخیره می‌شد.** شناسهٔ یکتای هر محصول
  از روی آدرس آن ساخته می‌شود، اما هنگام ساخت آن آدرس **کل رشتهٔ پرس‌وجو** حذف می‌شد. در فروشگاهی که
  آدرس محصول به شکل `/product?id=123` است، آدرس همهٔ محصولات یکسان می‌شد و همه روی هم ذخیره می‌شدند.
  حالا فقط پارامترهای تبلیغاتی (`utm_*`، `fbclid` و …) و پارامترهای صفحه‌بندی (`page`، `sort` و …)
  حذف می‌شوند و هر پارامتری که ممکن است شناسهٔ محصول باشد دست‌نخورده می‌ماند.
- **محصولات بدون قیمت نادیده گرفته می‌شوند.** چنین محصولی در هیچ مقصدی قابل انتشار نیست (ووکامرس
  `regular_price` لازم دارد و باسلام `primary_price` صفر را رد می‌کند) و فقط فهرست نتایج و جدول
  مغایرت‌گیری را شلوغ می‌کرد. حالا هم در استخراج و هم در درون‌ریزی فایل رد می‌شوند و تعدادشان در
  گزارش کار و در پاسخ درون‌ریزی نوشته می‌شود.

## نسخهٔ ۱.۱۲۱.۰ — نمایش مودال محصول مثل صفحهٔ واقعی محصول

- **توضیحات رندر می‌شوند، نه اینکه به‌صورت کد نمایش داده شوند.** پیش‌تر توضیحات به‌صورت متن خام داخل
  کادر لاگ دیده می‌شد و صفحهٔ یک فروشگاه واقعی کاملاً ناخوانا بود. حالا دقیقاً مثل چیزی که بازدیدکننده
  می‌بیند رندر می‌شود: تیترها، فهرست‌ها، جدول‌ها، تصاویر و لینک‌ها. چون این محتوا وارد `innerHTML`
  می‌شود، پیش از نمایش پاک‌سازی می‌شود: اسکریپت، iframe، فرم، رویدادهای `on…` و آدرس‌های
  `javascript:` حذف می‌شوند و لینک‌ها در تب جدید باز می‌شوند.
- **سلکتور تازهٔ «جدول مشخصات».** کافی است بلوک مشخصات را انتخاب کنید تا ردیف‌ها به‌صورت جفت
  نام/مقدار استخراج شوند. سه ساختار رایج پشتیبانی می‌شود: جدول (`tr`/`td`)، فهرست تعریفی
  (`dt`/`dd`) و فهرست «نام: مقدار». ردیف‌ها در مودال محصول به‌صورت جدول نمایش داده و همراه محصول
  ذخیره می‌شوند.
- **انتخابگر بصری قابل توقف شد.** پیش‌تر همهٔ کلیک‌ها را می‌گرفت و نمی‌شد تب‌ها، کشویی‌ها و
  گالری‌های صفحهٔ محصول را باز کرد تا به فیلدهای داخلشان رسید. با دکمهٔ **⏸ توقف انتخاب** صفحه عادی
  کار می‌کند و با **▶ ادامهٔ انتخاب** می‌توانید همان بخش‌های تازه‌بازشده را انتخاب کنید. در هر دو نسخه.

## نسخهٔ ۱.۱۲۲.۰ — توضیح «۱٬۲۰۰ از ۲۰»: سایت یک صفحه را تکرار می‌کرد

این دو عدد دو چیز متفاوت را می‌شمردند: عدد اول همهٔ **آیتم‌های خام اسکن‌شده** بود و عدد دوم تعداد
**محصولات یکتا**. فروشگاهی که برای همهٔ شماره‌صفحه‌ها همان ۲۰ محصول را برمی‌گرداند، ۶۰ × ۲۰ = ۱٬۲۰۰
آیتم اسکن می‌کند ولی فقط ۲۰ محصول یکتا دارد؛ پس «۲۰ محصول در نتایج» درست بود و «۱٬۲۰۰» گمراه‌کننده.
حالا هر دو عدد تعداد محصولات یکتا را نشان می‌دهند.

مهم‌تر اینکه محافظِ «این صفحه محصول تازه‌ای نداشت» فقط در حالت خودکار (`pages = 0`) اجرا می‌شد و با
تعداد صفحهٔ مشخص، همان صفحهٔ تکراری تا آخر خوانده می‌شد. حالا در هر حالتی اگر دو صفحهٔ پشت‌سرهم هیچ
محصول تازه‌ای نداشته باشند، استخراج متوقف می‌شود و هشدار می‌دهد که احتمالاً صفحه‌بندی کار نمی‌کند.

اگر فروشگاه واقعاً ۱٬۲۰۰ محصول دارد، «نوع صفحه‌بندی» و «مقدار صفحه‌بندی» پروفایل را بررسی کنید.
نسخهٔ کلودفلر از قبل روی صفحهٔ کاملاً تکراری متوقف می‌شد و تحت تأثیر نبود.
