# 🔁 حلقهٔ بازخورد اتصال (Connection Feedback Loop)

> نسخهٔ ۱.۳۲۷.۰+ — پاسخ به این مشکل: «پروفایل ایمالز-کفش زنانه (۱۱) وصل نمی‌شود و خطای ۴۰۳ می‌دهد».

## چرا یک حلقه، نه یک وصلهٔ ثابت؟

خطای ۴۰۳ یک پیام نیست، یک **رأی** است: دیوار آتش سایت مبدأ شکل درخواست ما را نپسندیده.
کدام بخش؟ سرآیند `Referer`؟ نبودِ `Sec-Fetch-*`؟ عاملِ کاربر دسکتاپ بدون کوکی؟ یا اصلاً IP سرور؟
هیچ‌کس از بیرون نمی‌داند. تنها راه درست این است که یک شکل درخواست بفرستیم، **پاسخ را بخوانیم**،
و اجازه دهیم همان پاسخ تلاش بعدی را انتخاب کند. این دقیقاً کاری است که این حلقه می‌کند:

```
تلاش  →  تشخیص پاسخ  →  انتخاب تلاش بعدی از روی تشخیص  →  راستی‌آزمایی محتوا  →  ذخیرهٔ روش برنده
  ↑                                                                                      │
  └──────────────────  اگر دوباره مسدود شدیم، خودکار از نو  ←──────────────────────────────┘
```

## سه فایل

| فایل | نقش |
| --- | --- |
| `worker-src/connection-loop.ts` | منطق خالص: جدول روش‌ها، تشخیص پاسخ، قانون‌های بازخورد، راستی‌آزمایی سلکتور. بدون هیچ وابستگی به زمان اجرا، پس در هر دو نسخه و در تست‌های آفلاین یکسان اجرا می‌شود. |
| `worker-src/url-shapes.ts` | نگارش آدرس: جایگزینی رمزگذاری‌امنِ پارامتر صفحه، نگارش‌های معادل یک آدرس، و «پزشک نگارش آدرس». |
| `worker-src/api-loop.ts` | همان روش برای جهت مخالفِ ترافیک: **حلقهٔ بازخورد ارسال** به APIهای مقصد (باسلام). بدون وابستگی به زمان اجرا. |
| `worker-src/source-mirrors.ts` | جدول آینه‌های عمومی (آخرین راه‌حل) و پاک‌سازی خروجی آن‌ها. |
| `worker-src/connection-heal.ts` | اتصال منطق بالا به دنیای واقعی در Cloudflare Worker (ترابری، حافظهٔ وضعیت، تنظیمات «روش اتصال مبدأ»). |

| --- | --- |
| `direct` | درخواست پیش‌فرض اسکریپر (همان چیزی که الان ۴۰۳ می‌گیرد) |
| `direct-referer` | افزودن `Referer` دامنهٔ خود سایت + `Sec-Fetch-*` + `Upgrade-Insecure-Requests` |
| `direct-hints` | افزودن Client Hints کروم (`Sec-CH-UA*`) و زبان فارسی |
| `direct-mobile` | عامل کاربر و هینت‌های مرورگر موبایل |
| `direct-search-bot` | معرفی به‌عنوان خزندهٔ موتور جست‌وجو (خیلی از سایت‌های ایرانی عمداً به آن اجازه می‌دهند) |
| `direct-warm` | اول صفحهٔ اصلی سایت گرفته می‌شود، کوکی و ارجاع آن برداشته و سپس صفحهٔ هدف درخواست می‌شود |
| `url-unescape` | آدرس با یک لایه رمزگذاری کمتر (برای آدرسی که دوبار انکد شده) |

| `url-lower-escapes` | کدهای درصدی با حروف کوچک |
| `worker` | از مسیر Worker واسط (IP دیگر) |
| `worker-ua` | Worker واسط + دستور فرستادن هدرهای مرورگر در بالادست (`x-proxy-ua`) |
| `mirror-allorigins` / `mirror-codetabs` / `mirror-jina` | آینهٔ عمومی: صفحه را از آدرس خودِ سرویس می‌گیرد و همان HTML را برمی‌گرداند |
| `mirror-wayback` | فقط تشخیص: نسخهٔ بایگانی‌شده |

### چرا نگارش آدرس هم یک «شکل درخواست» است؟

آدرس فارسی `https://emalls.ir/جستجو/کفش زنانه` چند نگارش معادل دارد
(`%20` یا `+` برای فاصله، حروف بزرگ یا کوچک در کدهای درصدی، و آدرسی که اشتباهاً دوبار انکد شده).
برای یک WAF یا لایهٔ IIS/ASP.NET این‌ها **درخواست‌های متفاوتی** هستند و یکی می‌تواند ۴۰۳ بگیرد و دیگری ۲۰۰.
پس حلقه آن‌ها را هم آزمایش می‌کند، نگارش برنده را کنار روش ذخیره می‌کند، و در جدول تلاش‌ها
**دقیقاً همان آدرسی که فرستاده شده** نمایش داده می‌شود. اگر نگارش آدرس مشکوک باشد
(مثلاً دوبار رمزگذاری‌شده) در بخش «🔤 بررسی نگارش آدرس» به زبان ساده گزارش می‌شود.
نگارش‌هایی که آدرس را عوض نمی‌کنند (مثلاً آدرس کاملاً انگلیسی) اصلاً امتحان نمی‌شوند تا درخواست بی‌خود فرستاده نشود.

## قانون‌های بازخورد

پاسخ هر تلاش به یکی از این تشخیص‌ها تبدیل می‌شود و همان تشخیص، مجموعهٔ تلاش‌های بعدی را تعیین می‌کند:

| تشخیص | معنی | گام بعدی |
| --- | --- | --- |
| `challenge` | صفحهٔ چالش ضدربات (کلودفلر/واف) | مسئله IP است، نه هدر: مستقیم به مسیر Worker |
| `forbidden` | ۴۰۳/۴۰۱ بدون چالش | اول هدرهای ارزان، بعد گرم‌کردن، در نهایت Worker |
| `throttled` | ۴۲۹ | همان روش، با مکث فزاینده (۱.۵ و ۳ ثانیه) |
| `server` | ۵xx | یک تکرار، سپس مسیر غیرمستقیم |
| `empty` | پاسخ ۲۰۰ ولی بی‌ساختار | هدرهای کامل‌تر، گرم‌کردن، Worker |
| `mismatch` | صفحهٔ واقعی ولی بدون نشانه‌های سلکتور فهرست | این دیگر مشکل اتصال نیست؛ حلقه صریحاً می‌گوید سراغ سلکتورها بروید |
| `network` | درخواست اصلاً نرسید | مسیر دیگر |

هیچ روشی دو بار امتحان نمی‌شود، سقف تلاش‌ها ۸ است، و اگر Worker واسط تنظیم نشده باشد
روش‌های غیرمستقیم اصلاً برنامه‌ریزی نمی‌شوند (به‌جایش در پیشنهاد پایانی گفته می‌شود که همان را تنظیم کنید).

## وقتی مسئله «چه‌کسی می‌پرسد» است، نه «چطور می‌پرسد»

اگر همهٔ شکل‌های درخواست و همهٔ نگارش‌های آدرس رد شوند، یعنی مسدودسازی بر اساس **IP/کشور** است و
هیچ هدری آن را حل نمی‌کند. در این حالت حلقه سراغ **آینه‌های عمومی** می‌رود: سرویس‌هایی که صفحه را از
آدرس خودشان می‌گیرند و همان HTML را تحویل می‌دهند.

* فقط `GET`، فقط صفحهٔ عمومی، بدون کوکی و بدون هیچ اطلاعات ورود.
* فقط آینه‌ای که **HTML دست‌نخورده** برمی‌گرداند قابل یادگیری است. سرویس‌هایی که صفحه را بازنویسی
  می‌کنند (مثل نوار ابزار و لینک‌های بازنویسی‌شدهٔ Wayback) فقط برای **تشخیص** استفاده می‌شوند و هرگز
  به‌عنوان روش دائمی ذخیره نمی‌شوند — وگرنه لینک محصول‌ها و سلکتورها آلوده می‌شد.
* همان راستی‌آزمایی سلکتور روی خروجی آینه هم اجرا می‌شود.
* آدرس سند همان آدرس اصلی سایت گزارش می‌شود تا لینک‌های نسبی درست حل شوند.
* اگر فقط نسخهٔ بایگانی باز شود، حلقه صریحاً می‌گوید: «آدرس و سلکتورهای شما سالم‌اند؛ مسدودسازی از
  سمت IP سرور است — یک Worker واسط با IP ایران تنظیم کنید».
* کلید خاموش‌کردن: «🪞 … از آینه‌های عمومی بخوان» در «روش اتصال مبدأ» (پیش‌فرض روشن).

## بازخورد به خودِ کاربر

* دکمهٔ «🧪 آزمایش دسترسی» دیگر فقط خطا نمی‌دهد: اگر شکست بخورد، همان‌جا حلقه اجرا می‌شود؛ اگر
  مشکل حل شد نتیجه با برچسب «با حلقهٔ بازخورد درست شد» برمی‌گردد و اگر نشد، جدول تلاش‌ها باز می‌شود.
* اگر خوددرمانیِ خودکار هم شکست بخورد، متن خطای استخراج دیگر «HTTP 403» خالی نیست؛ جملهٔ تشخیص
  حلقه به آن اضافه می‌شود.
* آخرین تشخیص هر دامنه در کلید وضعیت `net.loop:<دامنه>` ذخیره می‌ماند.

## راستی‌آزمایی: چرا «۲۰۰» کافی نیست

برخی وافـ‌ها به‌جای ۴۰۳ یک صفحهٔ خالی با وضعیت ۲۰۰ می‌دهند. برای همین وقتی پروفایل انتخاب شده باشد،
نشانه‌های **سلکتور فهرست همان پروفایل** (شناسه‌ها، کلاس‌ها، ویژگی‌ها) در متن پاسخ جست‌وجو می‌شود؛
اگر نباشند، تشخیص `mismatch` است و آن روش برنده حساب نمی‌شود.

## اشکال مهم جانبی که در همین نسخه رفع شد: صفحه‌بندی، نگارش آدرس را خراب می‌کرد

`pageUrl()` برای افزودن شمارهٔ صفحه از `URLSearchParams.set()` استفاده می‌کرد و این API
**کل کوئری را دوباره سریال می‌کند**: `%20` به `+`، `/` به `%2F` و `,` به `%2C` تبدیل می‌شد.
نتیجه این بود که صفحهٔ ۱ با یک نگارش و صفحهٔ ۲ با نگارش دیگری از همان عبارت فارسی درخواست می‌شد و
منبع سخت‌گیر برای دومی ۴۰۳ می‌داد. حالا پارامتر صفحه به‌صورت متنی و بدون دست‌زدن به بقیهٔ بایت‌های
کوئری جایگزین می‌شود (`worker-src/url-shapes.ts`، هر دو نسخه، آزمون در `worker-tests/url-shapes.test.mjs`).

## حافظه و خوددرمانی

* روش برنده (همراه نگارش آدرس) در کلید وضعیت `net.recipe:<دامنه>` ذخیره می‌شود.
* هر درخواست بعدی به آن دامنه **از همان روش شروع می‌کند** (یک درخواست، نه هشت‌تا).
* اگر سایت دوباره مسدود کرد، همان خطا حلقه را **خودکار** یک بار اجرا می‌کند (حداکثر هر ۱۰ دقیقه یک بار برای هر دامنه)
  و با روش تازه دوباره تلاش می‌کند. در Worker این کار در `sourceText()` انجام می‌شود و در Node داخل `safeText()`.

## استفاده

* **پنل:** «⚙️ تنظیمات ← روش اتصال مبدأ» ← دکمهٔ «🔁 حلقهٔ بازخورد اتصال». جدول کامل تلاش‌ها،
  وضعیت، تشخیص و پیشنهاد گام بعد نمایش داده می‌شود.
* **API:**

```http
POST /api/source/connection-loop
{ "profileId": "…", "url": "https://emalls.ir/…" }
→ { ok, host, recipe, route, attempts:[{round,label,route,status,verdict,note,bytes,ms}], advice }

POST /api/source/connection-recipe/forget
{ "url": "https://emalls.ir/…" }        # فراموش‌کردن روش ذخیره‌شده و یادگیری دوباره
```

## همان حلقه، این بار برای ارسال: «حلقهٔ بازخورد ارسال»

خواندن از مبدأ و نوشتن در مقصد یک مسئلهٔ مشترک دارند: **پاسخ، خودش راهنمای گام بعد است.**
باسلام APIهای جداگانهٔ هر میکروسرویس را با یک Gateway یکپارچه جایگزین کرد و در این Gateway
مسیر ویرایش محصول دیگر زیر غرفه نیست:

```http
ساخت   POST  https://openapi.basalam.com/v1/vendors/{vendor_id}/products
ویرایش PATCH https://openapi.basalam.com/v1/products/{product_id}        ← بدون شناسهٔ غرفه
```

ارسال‌کنندهٔ قدیمی همیشه `PATCH /v1/vendors/{vendor_id}/products/{id}` را می‌زد و همیشه
۴۰۴ می‌گرفت. دقیقاً همین ۴۰۴ از یک علت دیگر هم می‌آید: محصولی که در پنل باسلام حذف شده و
شناسه‌اش در پایگاه دادهٔ ما مانده است. این دو علت از روی **یک** درخواست قابل تفکیک نیستند؛
به همین دلیل اینجا هم یک حلقه لازم است، نه یک آدرس ثابت.

| پاسخ مقصد | برداشت حلقه | گام بعد |
| --- | --- | --- |
| `2xx` | پذیرفته شد | همین مسیر در `api.shape:basalam:create` یا `…:update` ذخیره می‌شود |
| `404` / `405` / `410` | این مسیر وجود ندارد | مسیر بعدی از جدول شکل‌ها |
| `401` | توکن پذیرفته نشد | توقف فوری؛ آدرس دیگر چیزی را عوض نمی‌کند |
| `403` | توکن دسترسی `vendor.product.write` ندارد | توقف فوری با همین جمله |
| `400` / `422` | مسیر درست است، محتوای محصول ایراد دارد | توقف؛ فقط دستهٔ بعدی پروفایل امتحان می‌شود |
| `429` | محدودیت نرخ | همان مسیر با مکث فزاینده (۱.۵ و ۳ ثانیه) |
| `5xx` | خطای سرور مقصد | همان مسیر، یک تکرار |

**تشخیص کلیدی:** اگر *همهٔ* مسیرهای شناخته‌شدهٔ ویرایش ۴۰۴ بدهند، مشکل از مسیر نیست و آن شناسه
روی باسلام وجود ندارد؛ گزارش حلقه `retryAsCreate` می‌شود و ارسال‌کننده محصول را دوباره **می‌سازد**
به‌جای اینکه تا ابد یک شناسهٔ مرده را ویرایش کند.

پیش از اولین تلاش، آدرس پایهٔ API هم اصلاح می‌شود (`normalizeApiBase`): اسلش اضافهٔ انتها، آدرس خالی،
یا نبودِ بخش نسخه (`/v1`) هر سه به‌تنهایی باعث ۴۰۴ می‌شدند.

متن خطایی که کاربر می‌بیند دیگر «HTTP 404» خالی نیست؛ تشخیص حلقه به‌علاوهٔ جدول کوتاه
`PATCH /v1/products/123 → 404 | …` به آن اضافه می‌شود و آخرین گزارش هر نوع نوشتن در
`api.loop:basalam:<create|update>` می‌ماند. ویرایش‌های نگهداری (بایگانی/تغییر وضعیت در
`rawbasalamUpdateShop`) هم از همین حلقه می‌گذرند.

آزمون: `worker-tests/api-loop.test.mjs` — ۱۰ تست آفلاین با یک باسلامِ ساختگی (۴۰۴ روی مسیر غرفه،
پاسخ سالم روی مسیر رسمی)، به‌علاوهٔ سنجاق‌های هم‌ترازی دو نسخه.

## همان حلقه، این بار برای خودِ میزبانی: «تشخیص محیط میزبانی»

یک بیلد ثابت روی VPS سالم کار می‌کند و روی هاست اشتراکی سه شکایت می‌سازد: «فونت اعمال نمی‌شود»،
«اندازهٔ فونت عوض نمی‌شود» و «منبع ۴۰۳ می‌دهد». این‌ها سه باگ نیستند؛ سه نشانه از دو تفاوت محیط‌اند:

1. **ریشهٔ نصب.** روی VPS برنامه روی ریشهٔ دامنه است، روی هاست زیر یک پوشه (مثلاً
   `example.com/app/…`) پشت پراکسی. هر آدرس مطلقی که با `/` شروع شود از آن پوشه بیرون می‌زند و به
   سایت اصلی می‌خورد؛ مرورگر به‌جای CSS یک صفحهٔ HTML می‌گیرد و بی‌صدا به Tahoma برمی‌گردد.
2. **خروجی اینترنت سرور.** فایل `woff2` را خود برنامه از CDN می‌گیرد و سرو می‌کند؛ اگر خروجی هاست
   بسته باشد پاسخ ۵۰۲ است و باز هم «فونت اعمال نشد» دیده می‌شود. همین محدودیت است که مسیر مستقیم و
   حتی آینه‌های عمومی را برای منبع می‌بندد و ۴۰۳ را روی هاست ماندگار می‌کند.

`worker-src/host-diagnosis.ts` (مشترک بین هر دو نسخه، بدون وابستگی به رانتایم) همان الگوی حلقه را
روی این سؤال‌ها اجرا می‌کند: هر بررسی یک پرسش واقعی است و **پاسخ تعیین می‌کند پرسش بعدی چیست**.

| پرسش | پاسخ | گام بعد |
| --- | --- | --- |
| `GET {publicBase}/assets/fonts/vazir.css` | HTML برگشت | «از مسیر برنامه بیرون رفته» — پرسش از فایل فونت بی‌معنی است و متوقف می‌شود |
| همان | CSS سالم | حالا فایل `vazir-400.woff2` پرسیده می‌شود |
| `GET …/vazir-400.woff2` | ۵۰۲ | نوبت CDNها: fontcdn، jsDelivr، unpkg مستقیم از سرور |
| CDNها | همه بسته | «خروجی اینترنت هاست بسته است» + راه‌حل `data/fonts` یا فونت سیستم |
| CDNها | یکی باز | «شبکه سالم است، مشکل در مسیر سرو فونت است» |
| `GET {sourceUrl}` | ۲۰۰ | چیزی پرسیده نمی‌شود |
| همان | ۴۰۳/۴۲۹/بی‌پاسخ | همان آدرس از آینهٔ عمومی پرسیده می‌شود |
| آینه | سالم | «IP هاست مسدود است؛ آینه‌ها را روشن بگذارید» |
| آینه | بسته | «خروجی محدود است؛ در روش اتصال مبدأ حالت Worker را با آدرس نصب سالم (VPS) بگذارید» |

به‌علاوه یک رفت‌وبرگشت نوشتن تنظیمات انجام می‌شود؛ اگر ناموفق باشد، علت «انتخاب فونت بعد از
بارگذاری دوباره برمی‌گردد» همان‌جا نام برده می‌شود.

اندپوینت: `GET /api/diag/host` در هر دو نسخه، و دکمهٔ «🩺 تشخیص محیط میزبانی» در تنظیمات عمومی.
هیچ توکنی در پاسخ نیست.

رفع‌های همراه این تشخیص: آدرس فونت‌ها در صفحه و داخل شیت **نسبی** شد (`assets/fonts/…` و
`url("./vazir-400.woff2")`) تا نصب زیرپوشه‌ای از کار نیفتد، مسیر `…/assets/fonts/*` زیر پوشهٔ پنل هم
سرو می‌شود، و انتخاب فونت/اندازه/پوسته همان لحظه اعمال می‌شود نه بعد از بارگذاری دوباره.

آزمون: `worker-tests/host-diagnosis.test.mjs` — ۱۱ تست آفلاین با میزبانی‌های ساختگی (ریشه، زیرپوشه،
CDN بسته، منبع مسدود با/بدون آینه، تنظیمات فقط‌خواندنی) به‌علاوهٔ سنجاق‌های صفحهٔ پنل و هر دو نسخه.

## تست

`worker-tests/connection-loop.test.mjs` — ۲۰ تست آفلاین با یک ترابری ساختگی که رفتار واقعی
ایمالز را بازتولید می‌کند (۴۰۳ به درخواست خام، صفحهٔ چالش به هدرهای آرایشی، پاسخ سالم از مسیر Worker)،

صفحه‌بندی رمزگذاری‌امن را پوشش می‌دهد.
